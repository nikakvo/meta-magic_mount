1What this module does

Most root modules change the system by shipping files: a binary in system/bin, a library in vendor/lib64, an app in product/app. Those files have to be placed over the real, read-only partitions at every boot, without touching the partitions themselves. That job is called mounting, and on KernelSU it is done by a metamodule.

Magic Mount is such a metamodule. At boot it takes the files of every other module and makes them appear in /system, /vendor, /product, /system_ext, /odm and any extra partitions you add. Nothing on the real partitions changes: turn a module off, reboot, and its files are gone.

Only one metamodule can be active. On current KernelSU, modules are installed without one but their files are not mounted, so every module that ships system files depends on it.

Works with

  • KernelSU and its forks, such as SukiSU-Ultra
  • APatch (without Unmount for hidden apps, which needs KernelSU)
  • arm64, armv7 and x86_64 devices; the installer picks the right binary

Magisk is not supported. It mounts modules itself, and the installer refuses to install there.

Why "magic"

The name comes from Magisk's classic technique. Each module file is bind-mounted over its target. When a module adds a file that does not exist on the device, the folder around it is rebuilt as a copy in memory (tmpfs) that mirrors the original contents plus the new file, and that copy is put in place. The result behaves like a normal system folder, and it is gone at the next reboot.

2What happens at boot

KernelSU runs Magic Mount's metamount.sh early in boot, in post-fs-data. By then module updates have been applied, removed modules are gone, and every module's post-fs-data.sh and system.prop have run. In order, the script:

  • moves the previous boot's log to mm.log.old
  • re-applies the modules you switched off in the Modules tab (see 5)
  • records the state of every module and a copy of the configuration, so the interface can later tell what this boot actually did
  • runs the mount program mmd, which does the real work and writes mm.log
  • records the result: success or failure, exit code, when it ran and how long it took
  • on KernelSU, tells the system that modules are mounted

At that point Android has not set the clock yet; on many phones it still shows a date from long ago. Times are therefore measured from the moment the phone started. Later, once the phone has finished starting and the clock is set, service.sh adds the real start time of this boot to the record. It waits at most 10 minutes; without a network the clock may stay unset, and then no time is recorded for that boot.

Magic Mount never blocks boot. If mounting fails, or the program is missing, the phone still starts normally. Module files are then simply not applied, and the Last boot card says so.

mmd is not a background service. It runs once, usually for a fraction of a second, and exits. There is no daemon and no process ID to watch. The Last boot card shows when it ran and how long it took.

3How module files are applied

Partitions

system vendor product system_ext odm extra

These colors are used throughout the interface. Modules keep their files under system/: system/bin/x ends up in /system/bin/x, and system/vendor/lib/y.so in /vendor/lib/y.so. When a module is installed, Magic Mount adds the shortcut links (vendor → system/vendor and so on) that some modules expect.

Extra partitions, such as mi_ext on Xiaomi or my_stock on OnePlus, are read from the module's top folder (<module>/mi_ext/…). They are only handled when listed in Config and when the partition exists on the device.

Markers a module can use

markereffect
skip_mountFile in the module folder: none of its files are mounted. The module itself stays enabled, so its scripts still run.
disableSet by the manager when a module is disabled: nothing is mounted.
removeSet by the manager when a module is uninstalled: nothing is mounted.
.replaceFile inside a folder: that folder replaces the system folder instead of being merged into it. The trusted.overlay.opaque attribute has the same effect.
whiteoutAn empty character device (0:0) in place of a file hides that file on the system.

When several modules touch the same folder

Their files are merged. Modules installed with KernelSU's own layout (vendor/ next to system/, with a link system/vendor → ../vendor) are merged together with modules that keep everything under system/.

When two modules ship the same file

Only one copy can be mounted. Magic Mount goes through the modules in a fixed mount order, and the first module that ships a path wins it:

  • first the preferred modules, in the order you set (Conflicts card or Config)
  • then every other module, sorted by module ID

The order does not depend on install order or on the file system, so the same module wins at every boot. The same rule decides when one module ships a file and another ships a folder or a link with that name. A .replace folder is honored whichever module ships it: the folder's original files are hidden, and files other modules add to it still show.

Every such case is a conflict. The Conflicts card lists them, and each boot's log names them as warnings. Two modules shipping identical files is harmless and only counted.

4The Modules tab

Header

The installed version and the root implementation (KernelSU or APatch) as recorded at install time.

Last boot card

The colored edge shows the result at a glance:

  • green — everything mounted, e.g. "15 entries mounted from 5 modules. No failures."
  • amber — mounted, but some entries failed or were skipped. Open Logs.
  • red — mounting failed, the mount program is missing, or Magic Mount did not run during this boot
  • grey — nothing to mount, or Magic Mount has not run yet (just installed)

The line below it, "Ran 7.3 s after boot, took 0.12 s", is measured on the device's uptime clock. It only appears when the record belongs to the current boot. Modules that caused failures are listed by ID.

Module list

Only modules that ship files for a handled partition are listed; modules that only run scripts have nothing to mount. Each row shows:

  • the color bands and names of the partitions it touches
  • the module name and ID
  • a switch: off stops mounting this module's files, but leaves the module enabled. Its scripts, properties and sepolicy still apply. Useful for finding which module breaks something, without losing its settings.
  • a pending-change label, if any (see 5)
  • a note when needed:
    • Disabled in the manager / Will be removed at the next reboot. The switch is locked; change it in the manager.
    • Switched off by a skip_mount file this app did not create. The module's author ships it switched off, or it was set by hand. Switching it on deletes that file.

A module whose update is waiting is shown with the files of the new version.

Conflicts card

Below the list. It shows which modules ship the same files, checked against what the next boot will mount: switches, disabled modules and installed updates are already taken into account. The check runs mmd --dry-run, which reads the modules but mounts nothing.

  • A is used instead of B — B's copies of these files are ignored. Show files lists them; entries marked file, folder or link are a file in one module and a folder or link in the other.
  • Use B instead — puts B first in the mount order (Preferred modules), so B wins all its conflicts from the next boot on. This writes the configuration, so the "apply after reboot" line appears.
  • A empties a folder — A replaces a folder another module adds files to. Both still apply.
  • Clear order — back to plain module ID order.

The card also warns when another module that mounts module files is installed, such as a second metamodule or mountify. Two of them would mount the same files twice; remove the other one.

Reload list

Reads everything again: modules, boot records, configuration and log. Changes made in this interface show up immediately. Reload is for changes made elsewhere while the interface is open, such as disabling a module in the manager, installing an update, or editing a file by hand.

5Changes after reboot

Mounting happens once, at boot. Switching a module off does not remove files that are already mounted, and switching it on does not add them. Every change waits for the next reboot.

How the interface knows what is pending

At every boot, metamount.sh records which modules were mounted and which configuration was used. The interface compares the current state with that record:

  • Mounts after reboot — off (or new) now, on after reboot
  • Stops mounting after reboot — mounted now, off after reboot
  • Update installed, new files apply after reboot

The line at the bottom counts the module changes, and a separate line appears when the configuration was changed. A dot on the Modules tab shows the same thing from other tabs.

Switch something off and back on, and the label disappears, because nothing differs from the running boot anymore. The labels stay correct after switching tabs, closing the interface or reloading.

Before Magic Mount's first boot there is no record yet. Until then the interface compares with the state from when it was opened.

Each boot record carries the kernel's boot ID. If the newest record is from an earlier boot, Magic Mount did not run this time: nothing is mounted, the Last boot card turns red, and no labels are shown.

Your choices survive module updates

When the manager updates a module, it replaces the module's folder and the skip_mount file is lost. Magic Mount keeps its own list of the modules you switched off (skip_mount.list) and puts the file back at the next boot, before anything is mounted.

6The Config tab

settingwhat it does
Log detailNormal logs the overview and every problem. Detailed logs every file operation; turn it on only for troubleshooting.
Unmount for hidden appsRegisters every mount with KernelSU. Apps for which the manager's Umount modules option is on then see the original system. KernelSU only; not shown on APatch.
Preferred modulesModule IDs, comma-separated. When two modules ship the same file, the one listed first wins; the rest follow by module ID (see 3). The Conflicts card fills this in for you.
Extra partitionsPartitions beyond the built-in five, comma-separated, e.g. mi_ext, my_stock. Add one only if a module ships a folder for it.
Work directoryTemporary space used while mounting. Leave it empty: the first writable in-memory location among /mnt/vendor, /mnt, /debug_ramdisk is used, with /dev/.magic_mount as a fallback.
Mount nameThe source name these mounts show in /proc/mounts. Keep KSU unless you know why not.
Log fileWhere the log goes. The previous boot's log is kept next to it as .old. Empty turns file logging off.
Module directoryWhere installed modules live. Only change it if you know why.

Input is checked before saving: paths must be absolute and must not contain spaces, quotes or #, and partition names and module IDs must be valid. The five built-in partitions and system folders are refused as extra partitions. Problems are marked on the field.

Unsaved changes means the form differs from the file. Saved changes apply after reboot means the file differs from the configuration the current boot used. Reset to defaults only fills in the form; nothing is written until you save. The file is written in one step, so an interrupted save cannot leave half a file.

7The Logs tab

  • This boot / Previous boot — mm.log and mm.log.old
  • Wrap lines — wrap long lines instead of scrolling sideways
  • Only warnings and errors — the quickest way to see what went wrong
  • above the log: when the log was written (the log lines have no times of their own, so this tells the two boots apart), line, warning and error counts, and when it was read. Refresh reads the file again; it only changes after a reboot.
  • the written time comes from the boot records, not from the file, whose date is set before the clock is (see 2). When no reliable time exists it is left out rather than shown wrong: for the previous boot right after Magic Mount was installed or updated, or when the clock was not set within 10 minutes of that boot.
  • errors in red, warnings in amber, debug lines dimmed

Each run ends with a summary: modules processed, entries mounted, skipped, whiteouts and failures, plus the modules that failed. The Last boot card is built from it. Very long logs show the last 20000 lines.

With Normal log detail a boot writes a short log of a few dozen lines; that is expected. Detailed logs every file operation and grows to hundreds or thousands of lines.

To investigate a problem: Config → Log detail → Detailed, reboot, then open Logs. Set it back to Normal afterwards.

8Install, update & uninstall

Install

Flash the zip in the manager and reboot. The installer detects the root implementation, verifies every file against its checksum, picks the binary for the device's architecture and activates itself as the metamodule. If another metamodule is active, it is marked for removal and replaced at the next reboot.

If some modules already contain a skip_mount file that Magic Mount did not create, the installer lists them so nothing stays off unnoticed. It also lists other installed modules that mount module files (a second metamodule, mountify), since two of them would mount the same files twice.

Update

Flash the new zip over the old one. The configuration and your switch choices are kept.

Installing other modules

While Magic Mount is active, the manager runs its metainstall.sh when installing other modules. It keeps the usual module layout and adds the partition shortcut links. On KernelSU a module can also request hot install (MODULE_HOT_INSTALL_REQUEST=true), which puts it in place and runs it without waiting for a reboot. Its system files are still mounted at the next boot.

Uninstall

Uninstalling puts things back the way they were:

  • it removes only the skip_mount files Magic Mount created. Files shipped by module authors are left alone, so those modules stay as their authors intended.
  • it removes the /data/adb/metamodule link if it still points here
  • it deletes its own data: configuration, logs and boot records

When another module is uninstalled, the manager lets Magic Mount drop it from its list, so the list only ever names installed modules.

On current KernelSU, module files are not mounted without a metamodule. Install another one if you remove this one.

9Command line

Everything the interface shows is plain text, so it can be read from a terminal (for example Termux) with root:

su -c 'cat /data/adb/magic_mount/status'          # last run: boot id, result, exit code, timing, start time
su -c 'cat /data/adb/magic_mount/status.old'      # the same for the boot that wrote mm.log.old
su -c 'cat /data/adb/magic_mount/boot_state'      # each module as the last run saw it
su -c 'cat /data/adb/magic_mount/skip_mount.list' # modules switched off here
su -c 'cat /data/adb/magic_mount/mm.conf'         # configuration
su -c 'cat /data/adb/magic_mount/mm.log'          # this boot
su -c 'cat /data/adb/magic_mount/mm.log.old'      # previous boot

Keep the quotes: everything after su -c must be one argument.

The mount program

mmd is not on the system path; use its full path:

su -c '/data/adb/modules/meta-mm/mmd --version'
su -c '/data/adb/modules/meta-mm/mmd --help'

  -m, --module-dir DIR    module directory
  -t, --temp-dir DIR      work directory (default: automatic)
  -s, --mount-source SRC  mount name
  -p, --partitions LIST   extra partitions, e.g. mi_ext,my_stock
  -P, --priority LIST     preferred modules, most preferred first
  -l, --log-file FILE     log file ('-' for the screen)
  -c, --config FILE       configuration file
  -v, --verbose           detailed logging
      --no-umount         do not register mounts for KernelSU umount
  -n, --dry-run           mount nothing; print the mount order
                          and the conflicts of the next boot
  -V, --version           print the version

--dry-run is safe at any time. It mounts nothing and never writes the log file; its report is one tab-separated line per item:

su -c '/data/adb/modules/meta-mm/mmd --dry-run'

mmd-dry-run  1  v1.2.0
order     1  module-a  installed      # every enabled module, in mount order
order     2  module-b  update         # "update" = installed, applies at reboot
conflict  file  system/etc/hosts  module-a  module-b
result    ok  2  1                    # ok | empty | error, modules, conflicts

The order lists every enabled module, also those with nothing to mount (they simply take no part). IDs are sorted byte by byte, so IDs that start with a capital letter come first.

Conflict kinds: file (different content), same (identical), type (file, folder or link against each other), replace (a folder emptied by the first module). The first module named wins.

Do not run mmd without --dry-run on a running system: a second run would mount everything a second time. metamount.sh refuses to run twice during the same boot for this reason. Command-line options override the config file.

Configuration file

# /data/adb/magic_mount/mm.conf
module_dir=/data/adb/modules
mount_source=KSU
log_file=/data/adb/magic_mount/mm.log
debug=false
umount=true
# temp_dir=/dev/.magic_mount
# partitions=mi_ext,my_stock
# priority=module-a,module-b

One key=value per line. Lines starting with # are comments, keys are not case-sensitive, and a key without a value is ignored. debug and umount accept true/false, yes/no, on/off or 1/0. Hand edits apply at the next boot, as usual.

10Troubleshooting

A module's files do not show up

Check that its switch is on and that it has no note. If it is not in the list at all, it ships nothing under a handled partition, or uses an extra partition that is not listed in Config. Otherwise look at the Last boot card, then Logs → Only warnings and errors.

A module's file is there, but it is another module's version

Two modules ship that file. Open the Conflicts card on the Modules tab, tap Use … instead on the module you want, and reboot.

"Magic Mount did not run during this boot"

Usually one of these: the phone booted in safe mode (KernelSU then skips all modules), Magic Mount is disabled in the manager, or another metamodule is active. Fix the cause and reboot.

"Mounting failed" or failed entries

The modules at fault are listed on the card. Switch one off, reboot, and check again to confirm which module causes it. Detailed logging shows the exact file and the system's error.

Skipped entries

A module tried to add something inside a folder that could not be rebuilt in memory, usually one that exists only in the module and not on the device. That one entry is left out and the rest still mounts. Detailed logging names it.

The switch is greyed out

The module is disabled or marked for removal in the manager. Mounting cannot be changed for a module that will not be mounted anyway.

An app still sees module files

Turn on Unmount for hidden apps in Config (KernelSU only), enable Umount modules for that app in the manager, reboot, and fully restart the app.

The phone does not boot after installing a module

Magic Mount itself cannot block boot, but a module's files can break the system. Boot into KernelSU safe mode (press volume down repeatedly while the phone starts; see the KernelSU documentation) and disable the module, or remove its folder from recovery. Safe mode disables every module, so enable the others again afterwards.

The interface is blank

The manager did not provide the JavaScript bridge the interface needs. Open it from KernelSU, SukiSU, APatch or MMRL.

11File layout

/data/adb/modules/meta-mm/
├── mmd               the mount program
├── metamount.sh      boot: records, runs mmd
├── service.sh        after boot: adds the real start time
├── metainstall.sh    used when other modules are installed
├── metauninstall.sh  runs when another module is removed
├── uninstall.sh      cleanup when Magic Mount is removed
├── customize.sh      installer
├── aok               root implementation (KSU / APATCH)
└── webroot/          this interface

/data/adb/metamodule  → link to the active metamodule

/data/adb/magic_mount/
├── mm.conf           configuration (kept across updates)
├── mm.log            this boot
├── mm.log.old        previous boot
├── status            result, exit code, timing, boot id, start time
├── status.old        the same for the previous boot
├── boot_state        each module as the last run saw it
├── boot_config       configuration the last run used
└── skip_mount.list   modules switched off here

Everything you set lives in /data/adb/magic_mount, outside the module folder, because an update replaces the module folder completely.
